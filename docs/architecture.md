# 代码分层（四层）

这么分层的目的：以后换板子或者换电机的时候，不用把所有代码都推翻重写。

| 层 | 在哪 | 干啥的 |
| --- | --- | --- |
| Board | `board/` | CubeMX 生成的外设初始化、中断入口、链接脚本，跟板子硬件绑死 |
| BSP | `bsp/` | 把 HAL 包一层，统一好调用的接口；不操心电机/IMU 的具体协议 |
| Module | `modules/` | 管具体设备的寄存器、协议、单位换算；不碰 HAL 也不碰 RTOS |
| Service | `threads/` | 建 ThreadX 线程、定采样/控制节奏、管同步和出错处理 |

`libs/` 放独立的算法（PID、CRC、数学），谁都不依赖。

依赖方向是从上往下：Service 调 Module，Module 调 BSP 给的接口。BSP 不能反过来去引用 Module，中断里有数据了是通过事先注册好的回调通知上面的。

## 一些约定

- 接口用 `context + 函数指针` 这种轻量方式，不用 new/malloc 动态分配。
- Module 的构造函数只是把依赖存起来，不真的去动硬件；初始化要等 Board/BSP 准备好了再显式调用。
- SPI 一次完整的读取（片选拉低期间的地址 + dummy + 数据）是一个整体；如果总线上挂多个设备，锁要锁住整个事务，不能只锁一个字节。
- CAN 中断里只把收到的帧简短地发出去；控制线程读快照、算控制量、再发指令。不认识 ID 的电机不注册、不驱动。发送成功只是说帧进了邮箱，不代表电调真收到了。
- IMU 读失败就只发半帧，快照里有有效位、时间戳和错误码，接收方自己判断能不能用。

## 安全默认

电机型号没确定之前，驱动代码留着但服务默认不开。就算开了服务，也不等于电机会动：必须硬件确认过、有限幅、有正常反馈、收到了明确的指令，这些条件都齐了才行。超时或者模式切换会把 PID 积分清掉，出了故障不会自己偷偷恢复。

## 一层一层往下做

1. **Board**：从空的 IOC 配起，实际用 CubeMX 生成，只编译这一层，核对时钟和引脚。
2. **BSP**：链接进 Board，看参数检查、忙/错误返回、中断和 DMA 对不对。
3. **Module**：先在电脑上用假的端口测试（PID、寄存器、单位、CAN 报文），再交叉编译。
4. **Service**：接上真的 ThreadX，看中断向量、tick 分工、优先级、栈大小。

记住：编译过了不代表线接对了，模拟测试过了也不代表硬件上就对了，最后还是得上真板子量。
